## Design decisions

- **D-01 Python 3.14 on Flex** (default GA in `list-flexconsumption-runtimes`); local dev/CI on 3.13 (the code is pure Python, `requires-python >= 3.11`).
- **D-02 KQL reserved words.** In this workspace `title`, `latest` and `first` cannot be used as bare identifiers inside function bodies or queries (parse error SYN0002). Output columns use `event_title`; no identifier is named `latest`/`first`.
- **D-03 Interval close rule.** An interval opens when the state becomes Unavailable (or Degraded) and closes at the next state *change* (Available, or the other of the two). Unknown rows and same-state duplicates are ignored. Per resource the state sequence is linear, so KQL needs no merge; `analytics/intervals.py` merges generically. Degraded is reported separately from Unavailable.
- **D-04 ARG ticks.** `todatetime(tolong(properties.X))` converts .NET ticks correctly (verified). `properties.Impact` is returned as an array, not a string; the query uses `parse_json(tostring(...))` which handles both. Zero ticks (year 0001) mean "not set".
- **D-05 REST adds depth ARG does not have.** Same subscription: ARG 15 events, REST (`queryStartTime=MM/DD/YYYY`, 365 d) 53 events, oldest `lastUpdateTime` 2025-12-02. The REST backfill and the ARG snapshot are both ingested; precedence arg > rest > activitylog per (subscription, tracking id).
- **D-06 Activity Log REST** supports `ge`/`le` but rejects `lt`; category cannot be filtered server-side. The backfill fetches one-day slices in parallel with `$select`, caches the token, retries 429/5xx with backoff, and filters ResourceHealth client side (~3 min for 89 days on a busy subscription).
- **D-07 Stale open intervals.** In the sandbox, 40 Resource Health "Unavailable" intervals (VM scale-set instances, VMs) never received a closing event - typically resources that were scaled in or deleted - and added up to ~1.8 million "downtime" minutes (availability 99.77 % with 18 tracked events). An interval that is still open more than 3 days after it started is flagged `stale_open`, kept for inspection (Resources page) and excluded from downtime and availability. This is an assumption that may hide a genuine multi-day maintenance; the threshold is in `analytics/intervals.py` (`STALE_OPEN_AFTER`) and `kql/AzMaintenance_ResourceIntervals.kql`.
- **D-08 Events without a mitigation time.** Many `Resolved` Service Health events carry no `ImpactMitigationTime`; computing exposure to now() produced 6,000+ hour "events". `is_open` now depends on status only; the window of a resolved event with no mitigation time ends at its last update (`end_basis = last_update`); open events end at now() and are excluded from the forecast (duration unknown).
- **D-09 Region on Resource Health rows.** Resource Health events carry no region, so planned/unplanned classification matches planned windows on subscription + service (via the catalog's ARM types) + time overlap, not region (method item 2 asks for region). Impact: a planned event in region A can classify a same-service interval in region B as Planned. Mitigation: VM annotations take precedence when present.
- **D-10 Forecast inputs.** Effective window W = min(365 d, coverage) where coverage starts at the REST backfill range start (or the first collector run). Duration per event = Resource Health Unavailable minutes overlapping the event for the same subscription + service, else the Service Health window; the basis is labelled per scope (`resource_health` only if every event has it). Overlap = 0 is treated as "not measured".
- **D-11 SLA percentages are blank** in `reference/service_catalog.csv` (never invented). `tools/load_reference.py` rejects an SLA without `sla_source_url` and `sla_verified_on`.
- **D-12 Taxonomy.** The catalog proposed 45 services across IaaS / PaaS / Network / Data / Identity / AI; it must be confirmed by the customer. Service Health service names not in the catalog show as category "Unmapped".
- **D-13 PIR windows.** The improved parser (word boundaries, narrow no-break spaces, lower-case "between") leaves 0 of 79 live PIRs unparsed (data-health "PIR window parse failures" = 0) and removes the poc's false category ("Central" matched "entra"). On the 80 poc fixtures it parses 79 on its own plus the CrowdStrike one via override. One regex result for `VVTQ-J98` was a 1-minute false positive, so `reference/pir_overrides.csv` now always wins over the regex. `1VT1-LX0` (CrowdStrike) states no window: override with a blank window, excluded from duration statistics.
- **D-14 Workbook.** Generated by `tools/build_workbook.py` (queries live in `kql/workbook/*.kql`, `//#include _prelude`). Every query and function runs without error against the sandbox (`tools/run_kql_checks.py`, 53/53 with synthetic data). **The workbook was not opened in the Azure portal by this build**, so parameter rendering (multi-select "All" = `*`, time-range token expansion `{TimeRange:start}`) follows the documented syntax but is not visually verified.
- **D-15 Synthetic rows.** `tools/seed_fixtures.py` loads rows with `is_synthetic=true` in a synthetic subscription id; every production function filters them out. The functions take `includeSynthetic:bool=false` so the checks can include them.
- **D-16 VM annotations module** (`kql/arg/vm_annotations.kql`) is unverified: the sandbox has no VMs with annotations (0 rows from `HealthResources`). It stays behind `AOL_ENABLE_VM_ANNOTATIONS`.
- **D-17 Azure Functions cannot be deployed in policy-governed subscriptions (superseded by D-21).** A policy above the subscription (not visible in the subscription's own assignments) forces `publicNetworkAccess: Disabled` on every new storage account: an explicit `Enabled` in the template or CLI is switched back to Disabled (probed 18 Nov 2026). Flex Consumption deploys code through the platform's own access to that storage, so the OneDeploy extension fails with `InaccessibleStorageException ... 403` and the Function app never runs code. Two real deployments hit this: a throw-away test group and a clean one-click deployment by the repository owner. I did not bypass the policy.
- **D-18 Quarterly report** is a CLI (`python -m reporting.render_report`), not a timer.
- **D-19 Workbook visual design** (17 Nov 2026). Pages now use KPI tiles with status icons, a "what needs your attention" checklist, donut/bar/column charts (orange = unplanned, blue = planned), a map, and grids with bars, heat colours and status icons. The Workbook JSON ids used (grid formatter 3 heatmap, 4 bar, 6 date, 12 big number, 18 thresholds; tile `rightContent` icons; `map` with `locInfo: AzureLoc`) come from the public sample workbooks and docs and were **not checked in the portal by this build**; a wrong id degrades the look (plain value) rather than erroring. The queries behind every visual run clean against the sandbox (`tools/run_kql_checks.py`). Bicep `loadTextContent` is limited to 131,072 characters, so the deployed file is the minified `workbook/workbook.deploy.json` generated beside the readable `workbook.template.json`.
- **D-20 One-click deployment** (17-18 Nov 2026). `infra/azuredeploy.bicep` (subscription scope, compiled to `infra/azuredeploy.json`) creates the resource group and deploys `main.bicep` into it, grants the collector identity Reader on the subscription, and creates the Activity Log export. The first version deployed code to a Flex Consumption Function app with the OneDeploy extension; see D-17 for why that was replaced.
- **D-21 Collector as an Azure Container Apps Job (no storage account).** Replaces the Function app. `infra/modules/collectorjob.bicep`: a Container Apps environment (consumption, logs to the workspace through a diagnostic setting, no keys) and one scheduled job (`15 * * * *` UTC, 0.5 vCPU / 1 GiB, system-assigned identity) on `mcr.microsoft.com/azurelinux/base/python:3.12`. Each run installs `requests` (this image has no CA bundle for plain `urllib`), downloads `release/app.zip` from the public repo, installs `requirements.txt` and runs `python -m collector.job collect`. State (watermarks, bootstrap-step markers) is stored as rows in `AzMaintenanceIngestHealth_CL` (`source = state:<key>`, `state_value`), so Table Storage is gone. `src/collector/job.py` bootstraps step by step (a failed step is retried alone next hour) and then runs tasks when due (Service Health and inventory daily, VM annotations every 6 h, PIRs monthly from day 2, planning ranges daily). **Verified in the policy-governed sandbox (18 Nov 2026) with probe jobs:** the container reached `raw.githubusercontent.com` and PyPI, `requests` downloaded the package, the managed identity got a token and called Azure Resource Manager (HTTP 200); `appLogsConfiguration` must be omitted or `azure-monitor` (the value `none` is rejected). The supply-chain trade-off is that the job runs whatever `release/app.zip` contains on the default branch at the time of each run: pin `packageUri` to a commit or tag, or fork, to control it.
- **D-22 End-to-end verification of the one-click deployment (18 Nov 2026, policy-governed sandbox).** A real deployment of infra/azuredeploy.json from the public GitHub URL into a new resource group succeeded for every resource (workspace, 9 tables, DCR, 10 functions, Workbook, alert, Container Apps environment and job, role assignments). The first job run failed at start-up (exit code 2) because the embedded shell script carried CRLF line endings from a Windows checkout; the template now strips CR and the Bicep sources are LF. After the fix: the bootstrap loaded everything in about 5 minutes (45 catalog rows, 79 PIRs, 72 distinct-event rows, 407 Resource Health rows, 48 inventory rows); the scheduled run at :15 fired on its own and ran only what was due; the forecast ran once the 45-minute delay passed (364 planning rows, customer and PIR baselines); all 85 workspace and Workbook query checks passed on the fresh workspace. A scheduled run fetched 10 instead of 79 public PIRs once (page 2 returned an empty page): the fetcher now retries an empty page after a full page and reports a truncated fetch as partial. The test resource group and the test identity's subscription-level Reader role were removed afterwards. Not verified: a second consecutive day of runs, and the Workbook rendering of the new visuals in the portal (D-19).
